# recap-now

긴 대화를 하다 보면 사용자는 자신이 원래 무엇을 하려고 했는지 놓치기 쉽다. 이 스킬은 대화를 한 걸음 떨어져서 읽고, **최종 목표**와 **핵심 문제** 두 가지만 짧게 되짚어 준다. 목적은 상세한 회의록이 아니라 방향 확인이다. 그래서 짧을수록 좋다.

## 하는 일

1. 지금까지의 대화 전체를 읽는다. 처음에 꺼낸 말뿐 아니라 중간에 바뀐 방향, 사용자가 정정한 부분, 결정된 사항까지 본다. 나중에 한 말이 처음 한 말보다 현재 의도에 더 가깝다.
2. 곁가지(탐색하다 만 주제, 이미 버린 선택지, 사소한 구현 디테일)는 걸러낸다.
3. 아래 형식으로 답한다.

## 출력 형식

```
**최종 목표**: <사용자가 결국 이루고 싶은 것, 한 줄>
**핵심 문제**: <그 목표를 가로막고 있어 지금 풀어야 하는 것, 한 줄>
```

- 각 항목은 한 줄, 되도록 한 문장으로 쓴다. 사용자가 쓴 표현과 용어를 그대로 살려야 "내 얘기를 이해했다"고 느낀다.
- 목표는 "무엇을 만들고 싶은가/이루고 싶은가", 문제는 "무엇이 막혀 있는가/무엇을 결정해야 하는가"다. 둘을 섞지 않는다. 목표가 수단(예: 특정 도구 사용)으로만 쓰였다면 그 수단이 달성하려는 결과로 올려서 쓴다.
- 서론, 칭찬, 대화 전체 요약은 붙이지 않는다. 두 줄이 답의 전부다.

## 모호할 때

대화가 목표를 하나로 좁히지 못하면 추측으로 단정하지 말고 이렇게 한다.

- 가장 가능성 높은 해석을 위 두 줄에 쓴다. 근거는 최근 발화와 사용자가 반복해서 돌아온 주제다.
- 다른 해석이 실제로 있을 때만 끝에 한 줄로 덧붙인다: `다른 해석: <대안 한 줄>`
- 대화에 정보가 거의 없어 요약할 거리가 없으면, 지어내지 말고 아직 목표가 드러나지 않았다고 짧게 말한 뒤 무엇을 하려는지 한 문장으로 물어본다.

대안을 항상 붙이는 것은 아니다. 해석이 분명한데 습관처럼 대안을 달면 짧고 명확하다는 이 스킬의 장점이 사라진다.

## 예시

대화: 사용자가 사이트 로그인 버그를 얘기하다가, 쿠키 설정, 배포 환경 차이, 디자인 수정까지 번졌고 마지막에 "결국 배포하면 로그인이 풀리는 게 제일 문제네"라고 말함.

```
**최종 목표**: 배포된 사이트에서도 로그인이 안정적으로 유지되게 하는 것
**핵심 문제**: 배포 환경에서만 로그인 세션이 풀리는 원인(쿠키 설정 차이로 추정)을 찾는 것
```
